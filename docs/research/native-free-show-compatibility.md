# FreeShow data and compatibility inventory

Research for [Inventory the existing FreeShow data and compatibility surface](https://github.com/ccfii-engineering/ccfii-free-show/issues/30), under the [CCFII native FreeShow successor map](https://github.com/ccfii-engineering/ccfii-free-show/issues/24).

## Evidence boundary

Local observations below are from the `main` snapshot `49031d95` (FreeShow 1.13.2, `package.json`). “Lossless” is used narrowly for structures preserved or copied without conversion in the inspected code. The existence of a JSON parser, importer, or exporter does not establish compatibility across releases or complete fidelity. The TypeScript interfaces are application data shapes, not a published validation schema.

The untracked `docs/native-feature-selection.md` in the shared checkout is user working context, not part of this `main` snapshot. It marks D01–D11 selected; this inventory makes no scope recommendation.

## Persisted artifacts and locations

The default data root is `Documents/FreeShow`; the path can be configured. Upstream’s data page says enabling “Save user settings at Data location” puts user projects, settings, templates, etc. in `Config` ([FreeShow data storage](https://freeshow.app/docs/data)). **The fork’s inspected store code differs for the `SETTINGS` store:** it is nonportable and remains at Electron’s app user-data path; only portable stores use the data-root Config directory. `SYNCED_SETTINGS` is portable and lives under Config. Local folder names/path logic are in [`files.ts`](https://github.com/ccfii-engineering/ccfii-free-show/blob/49031d95/src/electron/utils/files.ts#L314-L352), and the authoritative fork behavior is [`store.ts`](https://github.com/ccfii-engineering/ccfii-free-show/blob/49031d95/src/electron/data/store.ts#L43-L62).

### External media references

A show stores media entries as records that commonly point at absolute or relative filesystem paths; slide items can also refer to media by an id/path in `src`, `backgroundImage`, or layout background fields. The media bytes are not embedded by default. The exception is that the `Media` schema admits `base64`, and exported `.project` bundles can include media files. Project ZIP import extracts media to `<data root>/Imports/Projects`, then rewrites known path strings in the JSON; if a referenced original path already exists, extraction keeps using that path. This is observed import behavior, not a guarantee that arbitrary path layouts survive migration. See [`Show.ts`](https://github.com/ccfii-engineering/ccfii-free-show/blob/49031d95/src/types/Show.ts#L85-L109), [`import.ts`](https://github.com/ccfii-engineering/ccfii-free-show/blob/49031d95/src/electron/data/import.ts#L112-L205), [`export.ts`](https://github.com/ccfii-engineering/ccfii-free-show/blob/49031d95/src/electron/data/export.ts#L294-L350).

Upstream’s project format documentation says project files are JSON (or ZIP with `data.json`) and lists `files` for bundled media, overlays, and project/show data ([FreeShow `.project` format](https://freeshow.app/docs/format-project)). The user guide describes project exports as transfer bundles containing media and shows ([FreeShow project list](https://freeshow.app/docs/project-list)).

## Native FreeShow files, import, and export

- **`.show`:** Upstream documents a JSON show object under `.show` or `.json` ([FreeShow `.show` format](https://freeshow.app/docs/format-show)). This application’s working library files wrap the show object in `[id, object]`; its FreeShow show importer accepts either that pair or a bare object and assigns a new id to the latter. Saving/exporting a native show writes the pair. This gives a direct structural path for FreeShow JSON, with id/category/name normalization and old-value conversion during import; it is not a blanket cross-version round-trip guarantee. See [`importHelpers.ts`](https://github.com/ccfii-engineering/ccfii-free-show/blob/49031d95/src/frontend/converters/importHelpers.ts#L45-L99), [`save.ts`](https://github.com/ccfii-engineering/ccfii-free-show/blob/49031d95/src/electron/data/save.ts#L44-L74), [`export.ts`](https://github.com/ccfii-engineering/ccfii-free-show/blob/49031d95/src/electron/data/export.ts#L188-L199).
- **`.project`:** local importer accepts plain JSON or ZIP. ZIP expects `data.json`, may carry `files`, and may carry shows, overlays, actions, effects, media and project data. Local export emits plain JSON without files and a ZIP containing `data.json` plus selected media when files are included. Import can rewrite media paths and stores the source path on imported projects. Upstream format docs describe a `project`, `shows`, optional `overlays` and `files` shape; local project converter also accepts `parentFolder`, `effects`, `actions`, and `media`. See [`import.ts`](https://github.com/ccfii-engineering/ccfii-free-show/blob/49031d95/src/electron/data/import.ts#L112-L205), [`project.ts`](https://github.com/ccfii-engineering/ccfii-free-show/blob/49031d95/src/frontend/converters/project.ts#L15-L83), [`export.ts`](https://github.com/ccfii-engineering/ccfii-free-show/blob/49031d95/src/electron/data/export.ts#L294-L350), and [upstream `.project` format](https://freeshow.app/docs/format-project).
- **Other native files:** importer lists `.fstemplate`, `.fsaction`, `.fsstage`, `.fstheme` (with legacy aliases). It handles JSON directly; templates may also be ZIP bundles with `data.json` and media. Export paths exist for templates, themes, actions, and stage layouts. The inspected UI has no equivalent single-file export for all settings/profile/config state. See [`Import.svelte`](https://github.com/ccfii-engineering/ccfii-free-show/blob/49031d95/src/frontend/components/main/popups/Import.svelte#L15-L28), [`export.ts`](https://github.com/ccfii-engineering/ccfii-free-show/blob/49031d95/src/electron/data/export.ts#L31-L61).
- **Text/PDF/images:** `.txt` export flattens text in the active layout and does not serialize show structure or style. PDF and slide-image export serialize a rendered view. They are useful readable/rendered exports, not lossless project representations. Export choices are `project`, `show`, `txt`, `pdf`, `image`; see [`exportHelper.ts`](https://github.com/ccfii-engineering/ccfii-free-show/blob/49031d95/src/frontend/components/main/popups/export/exportHelper.ts#L7-L22), [`export.ts`](https://github.com/ccfii-engineering/ccfii-free-show/blob/49031d95/src/electron/data/export.ts#L206-L256).

## Backup and restore coverage

Manual backup builds a ZIP from portable stores, `SETTINGS`, all `.show` files, and (for cloud-sync payloads only) `MEDIA` and `.fsb` Bible files. Normal local backups do not include `MEDIA`, the actual media files, Bibles, `ACCESS`, `DRIVE_API_KEY`, history/cache/error/usage state, or the Electron `config` store; code explicitly comments that Bibles are not included in normal backups. Restore writes JSON settings and show files from the archive. Thus the code does **not** support calling a normal “Backup everything” archive a complete byte-for-byte local-library image: external media and several nonportable stores are outside its entries. Show/config file contents are archived as files, but restore may route individual files into existing stores and code does not version-migrate or validate schema semantics beyond JSON parsing. See [`backup.ts`](https://github.com/ccfii-engineering/ccfii-free-show/blob/49031d95/src/electron/data/backup.ts#L15-L87) and [`backup.ts`](https://github.com/ccfii-engineering/ccfii-free-show/blob/49031d95/src/electron/data/backup.ts#L111-L189).

### What the evidence supports

1. **Direct structural preservation is plausible for native FreeShow content**, especially `.show` tuples and native project bundles, because the application stores and exports its own JSON structures and accepts its own exported shapes. The importer still normalizes/repairs older show values, names, categories and media paths; there is no stated stable schema version or formal compatibility promise in the inspected local files.
2. **Third-party imports are conversion paths, not round trips.** The outputs are FreeShow `Show`/`Project` objects, not retained source documents. Unknown fields, source-specific layout semantics, animations, linked assets, macros and application settings are not shown as preserved generically. There are no third-party exporters in the current export choices.
3. **Rendered/document exports are intentionally reduced representations.** TXT flattens selected text; PDF/images capture presentation appearance. These do not preserve editable source semantics.
4. **Complete local state portability is narrower than “all data.”** Project ZIPs can include listed media, but regular backups omit external media and multiple nonportable stores. Profile/settings data has JSON storage and some backup coverage, but no standalone all-settings portable format was found.

## External-format search record

The version and format claims distinguish (a) this fork’s file picker/parser implementation, (b) upstream FreeShow’s advertised product support, and (c) the format’s vendor/maintainer documentation or source. Searches for publicly available, versioned primary schemas or complete file-format specifications did not find one for ProPresenter’s `.pro4`/`.pro5`/`.pro6`/`.proBundle` extensions, EasyWorship song `.db`, MediaShout `.ssc`/`.mdb`, VideoPsalm `.vpc`/JSON, SongBeamer `.sng`, SoftProjector `.sps`, EasiSlides XML, or VerseVIEW XML. Where vendor manuals/support pages surfaced, they establish workflows as stated above, but not a parser contract. The EasyWorship database-version claim in its vendor-hosted forum is a community member’s reply and is explicitly anecdotal, not vendor confirmation. In particular, the SongBeamer release page is not a file-format reference. Quelea maintainer documentation/source establishes QSP and OpenLyrics import paths, but not a compatibility guarantee for FreeShow’s importer. Microsoft’s Word/Office material establishes document packaging formats, not the extent of FreeShow’s text extraction. OnSong’s manual establishes its own `.onsong` syntax, while no FreeShow compatibility promise or tested OnSong version was found.

For fork behavior, the reviewed converter sources are [`easyworship.ts`](https://github.com/ccfii-engineering/ccfii-free-show/blob/49031d95/src/frontend/converters/easyworship.ts), [`mediashout.ts`](https://github.com/ccfii-engineering/ccfii-free-show/blob/49031d95/src/frontend/converters/mediashout.ts), [`songbeamer.ts`](https://github.com/ccfii-engineering/ccfii-free-show/blob/49031d95/src/frontend/converters/songbeamer.ts), [`videopsalm.ts`](https://github.com/ccfii-engineering/ccfii-free-show/blob/49031d95/src/frontend/converters/videopsalm.ts), [`quelea.ts`](https://github.com/ccfii-engineering/ccfii-free-show/blob/49031d95/src/frontend/converters/quelea.ts), [`softprojector.ts`](https://github.com/ccfii-engineering/ccfii-free-show/blob/49031d95/src/frontend/converters/softprojector.ts), [`easyslides.ts`](https://github.com/ccfii-engineering/ccfii-free-show/blob/49031d95/src/frontend/converters/easyslides.ts), [`verseview.ts`](https://github.com/ccfii-engineering/ccfii-free-show/blob/49031d95/src/frontend/converters/verseview.ts), [`chordpro.ts`](https://github.com/ccfii-engineering/ccfii-free-show/blob/49031d95/src/frontend/converters/chordpro.ts), and [`import.ts`](https://github.com/ccfii-engineering/ccfii-free-show/blob/49031d95/src/electron/data/import.ts).
