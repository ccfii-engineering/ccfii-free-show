# Portable PowerPoint renderer research

Date: 2026-10-25
Scope: choose an offline, cross-platform renderer for the default static-image PowerPoint import. This research note does not change the application, package manifests, or ADRs. The user's 2026-10-25 requirement supersedes ADR 0004's original “no new rendering engine” direction: a portable open-source renderer is now in scope.

## Recommendation

Advance @web-ppt/core 0.4.5 for a PPTX-first production integration spike. It is MIT-licensed, has one small runtime dependency (fflate), and returned browser-generated PNGs from one slide at a time without LibreOffice, a server, network access, native modules, or an installer. This fits FreeShow's retained-source, sequential PNG, cache, and static-show pipeline. The published package documents parsing both OOXML .pptx and legacy binary .ppt by file signature, but this research only validated a synthetic .pptx. Keep legacy .ppt and macro-enabled .pptm disabled until genuine files of each format pass fixtures and compatibility checks.

This is a candidate recommendation, not a release-readiness claim. Before shipping PPTX support, compare representative real decks against LibreOffice/PowerPoint, add parser input limits, and verify packaged Electron behavior on Windows x64/ARM64, macOS Intel/Apple Silicon, Linux x64/ARM64. Enable .ppt and .pptm only after authentic format-specific fixtures, including VBA presence for .pptm, are tested.

## Evidence from the isolated proof

A disposable project under /tmp installed the published npm artifacts; the repository manifests and lockfile were not touched. The fixture was generated as a real ZIP/OOXML .pptx using scripts/tests/helpers/pptxFixture.ts. It was 4:3 and contained a theme-colored slide-master bar, a theme-colored outlined shape, Arial text, and an embedded PNG. @web-ppt/core parsed the deck and slideToPng(pres, pres.slides[0], 1.5) returned a 45,730-byte image/png at 1440 × 1080 in headless Chromium. The result was visually inspected; the title, outline, master bar, and embedded picture appeared. No network request or LibreOffice process was involved.

The same fixture was passed through @office-kit/pptx 0.27.0 + @office-kit/pptx-preview 0.19.0. Its Node PNG API also rendered it in the bundled Electron runtime (Electron 37.10.3 embeds Node 22.21.1; the packages declare Node >=22.18.0). Its PNG output was 18,984 bytes at 1280 px width. Thus Office Kit is technically viable here; it is not disqualified by the embedded Node version.

A copy of the synthetic ZIP fixture renamed to .pptm also parsed with web-ppt. This checks that its parser is signature-based, not actual compatibility with a macro-enabled deck. No authentic .pptm or .ppt file was available in the checkout, so those formats remain production-spike checks.

## Format and feature boundaries

- **.pptx:** ZIP/OOXML, handled by web-ppt's OOXML parser. Verified only with the synthetic fixture in this research.
- **.ppt:** legacy CFB/OfficeArt binary. The project README documents a separate parser and the public parse() function checks the CFB magic signature. This format is not validated by the isolated proof; it must get a real-deck fixture and a UI responsiveness/cancel check before release.
- **.pptm:** macro-enabled OOXML ZIP. The same parser accepts a ZIP by magic and its preview reader deliberately defers ppt/vbaProject*; this suggests it treats the presentation as content and does not run macros. The renamed-file test was only the same ordinary PPTX ZIP, so a real macro-enabled deck and macro-presence test are still required. Keep .pptm explicit in import UI/filtering and never execute its VBA.
- **Fonts:** web-ppt parses usable embedded sfnt fonts and can unwrap uncompressed EOT containers. MTX-compressed EOT requires an injected decoder (setFontDecoder); without one, the font is skipped. Its optional @web-ppt/fonts package downloads substitutes from jsDelivr, so it must not be included for this offline requirement. With that package omitted, system fonts/embedded fonts and the renderer's fallback are all that are used. OS/2 fsType embedding permissions are not a packaging permission for FreeShow; treat font bytes as user-supplied deck content, keep them local, and test representative font licenses/embedding cases.
- **Images and vector content:** embedded PNG succeeded. The documented image parser handles common raster formats and SVG media; classic EMF/WMF are converted by the library's GDI decoder. SVG fallback (asvg:svgBlip plus raster fallback), WMF/EMF, and Office-exported SVGs were not exercised here. Add fixtures and verify fallback selection and safe raster output.
- **Themes, masters, shapes, charts:** the fixture confirmed a theme accent color and a slide-master shape plus an outlined shape. Complex placeholders, master/layout images, tables, SmartArt, and charts were not independently tested. Project docs claim classic chart types, while newer chartex types are listed as unsupported. Treat fidelity as feature-dependent and keep representative comparison captures in the follow-up spike.
- **Notes, media, and animation:** web-ppt can parse speaker notes, transitions, and animation batches, but this import intentionally rasterizes one static frame per slide. Notes/audio/video/transitions do not become FreeShow presentation behavior through PNGs; notes are not separately retained by the current ImportSource model.

## Integration plan for a production spike

1. Replace the default appearance-preserving PowerPoint converter in src/electron/data/renderedPowerPointImport.ts with a renderer adapter that opens the managed source, reports page count/version, returns one bounded PNG at a time, and closes/disposes its parse session. Keep PDF imports on PDF.js and keep editable conversion as an explicit separate path. Do not silently select the lossy editable converter on parse/render failure.
2. Run web-ppt inside an isolated Electron renderer job/window. Its documented renderer is browser-based; parsing a legacy .ppt is synchronous and has no public worker API. Do not run that work on the interactive main UI thread. The existing per-import lock, cancellation signal, progress reporting, cache key, managed source copy, and sequential output loop are good seams. On abort or error, terminate the isolated renderer and revoke its presentation asset URLs with pres.dispose().
3. Keep output capped by the existing 1920 × 1080 / 2,073,600-pixel page contract. Compute slideToPng scale from slide dimensions and output limits; verify returned dimensions before writing. Keep one page's canvas/output alive at a time and await PNG encoding before advancing.
4. Update ImportSource metadata compatibly: renderer name/version should identify web-ppt and the embedded Chromium version; make pdfPath optional for new PowerPoint imports (retain old records for rerender/backward compatibility), while preserving the original managed source, renderer version, resolution, cache key, and page paths. Include both renderer and Electron/Chromium versions in the cache key because browser text/layout behavior can change with Electron upgrades.
5. Preflight untrusted archives before parsing. The parser's preview path uses synchronous fflate.unzipSync and does not declare a total uncompressed-size, entry-count, image-dimension, or time budget. Add app-side limits for source bytes, declared ZIP uncompressed total/entry count, slide count, and image dimensions; reject oversized inputs with a clear error. Test cancellation against a deck that is still parsing and a deck with many large images.
6. Validate offline behavior with network disabled, .ppt, genuine .pptm with VBA present, embedded and missing fonts, SVG-with-PNG-fallback, WMF/EMF, theme/master/layout inheritance, and chart/SmartArt samples. Compare pages with LibreOffice and PowerPoint output; document unsupported fidelity cases. Run packaged builds on Windows x64/ARM64, macOS Intel/Apple Silicon, and Linux x64/ARM64.

The updated [ADR 0004](../adr/0004-preserve-powerpoint-appearance-by-default.md) records the approved portable PPTX direction and the superseded LibreOffice default. Implementation review, final validation, and release status remain tracked separately in that ADR. The isolation proof files are in /tmp/pptx-portable-poc (fixture generator and renderer proof) and /tmp/webppt-browser (Vite/Chromium PNG proof).
